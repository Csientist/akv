Platform Overview

Everything a farm operation needs

Designed for low-connectivity environments, Akavango keeps all your data local first and syncs intelligently via Appwrite TablesDB.

🐄

Asset Management

Track livestock and crops with full activity logs. Photo capture on registration, events logged per asset with timestamps.

🥛

Milk Logging

Session-by-session milk logs linked to individual animals. Live dashboard shows daily totals and trends.

🌿

Feed & Pasture

Track paddock rotation to prevent overgrazing, alongside supplemental feed costs and water/mineral issues.

📊

Monthly KPIs

Automated dashboards compute herd sizes, birth/death rates, and net profits natively via instant SQLite aggregates.

📦

Inventory Control

Feed, medicine, and equipment tracking with edit support. Know what's in stock before heading to the field.

💰

Financial Records

Sales and purchases with partial payment support. Instalment tracking across multiple payment milestones.

🔄

Bidirectional Sync

Outbox pattern ensures zero data loss. Migrated to Appwrite 1.8.0 TablesDB for atomic server-side upserts.

🔒

Secure & Private

PIN auth layer on top of Appwrite sessions. Credentials stored via flutter_secure_storage. Each user scoped by created_by.

Getting Started

Get Akavango Farm Manager running on your Android device. The app uses Appwrite 1.8.0+ terminology: "Tables" and "Rows". Appwrite Cloud (Frankfurt region) handles the backend.

Prerequisites

  • Flutter SDK ≥ 3.19
  • Android Studio or VS Code
  • Android device (API level 23 minimum)
  • An Appwrite Cloud account
  • Git

Flutter Setup

1

Clone the repository

git clone https://github.com/your-org/akavango-farm.git
cd akavango-farm
2

Install dependencies

flutter pub get

Appwrite Console Setup

Akavango uses the TablesDB architecture. Confirm these tables exist in your database:

Environment Config

Create a lib/config/app_config.dart file with your Appwrite credentials.

First Run

flutter run --debug
Technical Reference

Architecture

Akavango is built on a local-first principle. SQLite is the source of truth on-device, and Appwrite TablesDB is the sync target.

Service Architecture

🔄

SyncService

Drains the sync_queue outbox table. Uses tablesDB.upsertRow for atomic "create-or-update" operations, ensuring zero data loss and minimal network overhead.

⬇️

DownSyncService

Cursor-based pull using tablesDB.listRows. Uses sync_meta table to persist cursors so only new/updated rows are fetched since the last sync pass.

⏱️

AppRefreshService

Drives the 1000s background heartbeat. Exposes a stream that fires twice per tick — once for fast local reload and once after sync completes.

📸

Image Services

Pick → compress (JPEG, ≤200KB) → cache. ImageSyncService handles bucket uploads and pushing row metadata to the asset_images table.

Data Flow

Sync Architecture

Write local, sync smart

Every write hits SQLite immediately. SyncService drains the outbox queue when connectivity is available. Conflict resolution is "Appwrite wins," logged to sync_conflicts for audit.
