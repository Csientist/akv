Platform Overview

Everything a farm operation needs

Designed for low-connectivity environments, Akavango keeps all your data local first and syncs intelligently when a connection is available.

🐄

Asset Management

Track livestock and crops with full activity logs. Photo capture on registration, events logged per asset with timestamps.

🥛

Milk Logging

Session-by-session milk logs linked to individual animals. Live dashboard shows daily totals and trends.

🌿

Feed & Pasture

Track paddock rotation to prevent overgrazing, alongside supplemental feed costs and water/mineral issues.

📊

Monthly KPIs

Automated dashboards compute herd sizes, birth/death rates, and net profits natively via instant SQLite aggregates.

📦

Inventory Control

Feed, medicine, and equipment tracking with edit support. Know what's in stock before heading to the field.

💰

Financial Records

Sales and purchases with partial payment support. Instalment tracking across multiple payment milestones.

🔄

Bidirectional Sync

Outbox pattern ensures zero data loss. Sync fires on connectivity restore, on app unlock, and on a 1000s heartbeat.

🔒

Secure & Private

PIN auth layer on top of Appwrite sessions. Credentials stored via flutter_secure_storage. Each user scoped by created_by.

Getting Started

Get Akavango Farm Manager running on your Android device. The app targets Android-first (tested on your Android device) with iOS-ready architecture. Appwrite Cloud (Frankfurt region) handles the backend — you'll need a free Appwrite account.

Prerequisites

  • Flutter SDK ≥ 3.19 (flutter --version to check)
  • Dart SDK included with Flutter
  • Android Studio or VS Code with Flutter extension
  • Android device or emulator — API level 23 (Android 6) minimum
  • An Appwrite Cloud account (free tier works)
  • Git
iOS note: The architecture is iOS-ready. You'll need Xcode on macOS and an Apple Developer account for device builds.

Flutter Setup

1

Clone the repository

git clone https://github.com/your-org/akavango-farm.git
cd akavango-farm
2

Install dependencies

flutter pub get

Key packages from pubspec.yaml:

  • appwrite: ^21.0.0 — Appwrite Dart/Flutter SDK
  • sqflite — SQLite local database
  • image_picker — Camera and gallery access
  • flutter_image_compress — JPEG compression to ~200KB
  • flutter_secure_storage — Session persistence
3

Verify Flutter doctor

flutter doctor -v

All Android toolchain items should show ✓. Xcode warnings are acceptable if targeting Android only.

Technical Reference

Architecture

Akavango is built on a local-first principle: SQLite is the source of truth on-device, and Appwrite Cloud is the sync target. The payment layer is powered by Appwrite Functions in Go talking to Safaricom's Daraja API via a Cloudflare Worker. This very documentation is hosted on Appwrite Sites.

Service Architecture

🔄

SyncService

Drains the sync_queue outbox table to Appwrite Database. Fires on connectivity restore, on PIN unlock, and on the 1000s heartbeat from AppRefreshService.

  • Reads pending rows from sync_queue
  • Upserts each record to its Appwrite collection
  • Marks queue row as processed on success
  • Triggers DownSyncService after completion
⬇️

DownSyncService

Cursor-based pull of all 10 collections from Appwrite. Uses sync_meta table to persist per-collection cursors so only new/updated documents are fetched.

  • Reads last cursor from sync_meta
  • Fetches pages sorted by created_at ASC
  • Writes to SQLite, detects conflicts
  • Logs conflicts to sync_conflicts
⏱️

AppRefreshService

Drives the background heartbeat. Exposes a stream that fires twice per tick — once before and once after sync — so UI layers can show a loading state cleanly.

  • 1000s periodic tick
  • Immediate tick on app unlock
  • Pre + post sync stream events
📸

ImageService + ImageSyncService

Two-stage image pipeline. ImageService handles capture and local persistence. ImageSyncService handles upload and metadata push.

  • Pick → compress (JPEG, ≤200KB) → cache → SQLite row
  • Queue file for upload to asset-images bucket
  • Push metadata to asset_images collection
  • Download thumbnails on down-sync
🔐

SessionManager + PinService

Two-layer auth. Appwrite handles cloud sessions; PIN provides local unlock without requiring network.

  • SessionManager — holds userId in memory
  • Restored from flutter_secure_storage on start
  • PinService — hashes PIN into auth_config table
  • PIN unlock triggers immediate sync tick
🗄️

Local SQLite Schema

Version 2 schema with migrations handled via sqflite onUpgrade routines.

  • sync_queue — outbox for up-sync
  • sync_meta — per-collection down-sync cursors
  • auth_config — hashed PIN store
  • All 10 collection tables (mirrored from Appwrite)

Data Flow

Sync Architecture

Write local, sync smart

Every write hits SQLite immediately — the app never waits for a network round-trip. A sync_queue outbox table records each pending operation. SyncService drains the queue when connectivity is available.

Down-sync uses cursor-based pagination to pull all collections from Appwrite after every up-sync pass. Conflicts are resolved with "Appwrite wins" and logged for audit.

Outbox Pattern Cursor Pagination Conflict Audit Heartbeat Tick

User Action
    │
    ▼

    │
    ├─► sync_queue (outbox row appended)

    │
    ▼  [after up-sync]

    │

    ├─► SQLite (write new/updated rows)
    └─► sync_conflicts (on version mismatch → Appwrite wins)

Conflict Resolution Policy

Appwrite wins. When a down-sync document has a newer updated_at than the local SQLite row, the Appwrite version overwrites the local record. The overwritten local values are recorded in sync_conflicts with a conflict_id for full audit. Users can review conflicts via the long-press menu on the sync banner.

Cloud Infrastructure

Akavango's server-side is built entirely on Appwrite — Functions for backend logic, Sites for this documentation, and Appwrite Database as the sync target. M-Pesa integration is handled via a Cloudflare Worker that bridges Safaricom's Daraja API with the app's payment flow.

📱

M-Pesa STK Push — Appwrite Function

An Appwrite Function written in Go initiates the STK push to Safaricom's Daraja API. When a user triggers a payment in the app, the function requests the push prompt on the user's phone.

  • Runtime: Go on Appwrite Functions
  • Triggered by app via Appwrite SDK function execution
  • Calls Daraja /mpesa/stkpush/v1/processrequest
  • Returns CheckoutRequestID for callback matching
🔁

M-Pesa Callback — Appwrite Function

A second Go function receives the payment result callback from Safaricom. It validates the payload, updates the relevant financials and partial_payments records in Appwrite Database, and marks the transaction as settled.

  • Exposed as an Appwrite Function HTTP endpoint
  • Receives and validates Daraja callback body
  • Writes confirmed payment to financials collection
  • Creates row in partial_payments if instalment
☁️

Cloudflare Worker — Daraja Proxy

Safaricom's Daraja API requires specific headers and has CORS restrictions that conflict with direct requests from Appwrite Functions. A Cloudflare Worker sits between the two, normalising headers and routing requests transparently.

  • Proxies requests from the Go functions to Daraja
  • Handles CORS and header compatibility
  • Adds OAuth token injection for Daraja auth
  • Zero cold-start latency on Cloudflare's edge network
🌐

Appwrite Sites — This Documentation

This documentation site is deployed and hosted on Appwrite Sites — part of the same Appwrite project as the app's backend. No separate hosting provider needed.

  • Static HTML deployed to Appwrite Sites
  • Served from the same Appwrite project
  • Connected to the same repo — changelog stays in sync with the codebase
  • Zero external hosting dependencies

v0.2.1
2026 — Q1
Beta

Sync Orchestration — Internal Patch

Internal orchestration changes only. No new features, no schema changes, no UI changes. Behaviour is identical when online — patch purely improves offline behaviour and reduces unnecessary network calls.

↺ Changed — app_refresh_service.dart
  • Pre-flight connectivity check added to _tick() — if offline, the UI broadcast still fires (screens reload from local SQLite immediately) but the sync is skipped entirely, making zero API calls. Previously the tick would enter _runSyncLoop, travel through the connectivity gate inside it, and then abort — wasting the async overhead of starting the call chain
  • nudge() decoupled from sync — it now only broadcasts to UI screens and no longer triggers fullSync(). Writes are already queued in the up-sync outbox and will be pushed on the next connectivity event or periodic tick. Running a full bidirectional sync on every write was adding latency with no benefit, as the immediate down-sync pass would find nothing new
  • connectivity_plus import added — required for the pre-flight check in _tick()
↺ Changed — sync_service.dart
  • _isSyncing promoted to static bool — the sync guard was instance-level, but SyncService() is instantiated fresh at every call site, so each new instance started with _isSyncing = false, making the concurrency guard ineffective. Promoting to static makes it a true process-wide lock
  • listenForConnectivity now triggers fullSync() instead of processQueue() on reconnect — ensures down-sync runs immediately on connectivity restore, pulling any records pushed from another device while offline. Previously only the up-sync queue was processed on reconnection, leaving down-sync delayed by up to 1000 seconds
